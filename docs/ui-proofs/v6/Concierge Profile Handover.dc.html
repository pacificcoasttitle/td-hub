Concierge Profile — operator handover
17 Sep 2026 · td-hub @ main
1 · What the operator does
  1. Opens Reports in the hub, clicks New report, and picks Concierge Profile — the one type found by address rather than fed a dataset.
  2. Types the property address. It is resolved to exactly one property before anything is spent; an ambiguous address stops here with no charge.
  3. A cost gate opens: the property, who it's prepared for, the presenting rep, the comparable criteria, and credits used to date. It says plainly that this spends one SiteX credit.
  4. They type a prepared-for name, tick the acknowledgement, and click Generate — 1 credit. Cancel is focused by default and Enter never confirms.
  5. SiteX is called once and the eight-page PDF appears in the Reports list, offering Download and Comparables — re-rendering is free and never calls SiteX again.

5 · The money
The one charging route: POST /api/concierge/profiles. It is the only file that imports generateConciergeProfile, and a test asserts the criteria, render and pdf routes import neither it nor anything under integrations/sitex. A 200 costs one credit; any non-2xx costs nothing.

What stops a retry charging twice — and why it no longer does: the guard is one profile per order. The route calls getProfileForOrder before generating and returns 409 if a profile exists whose status is not failed. With the entry point on the Reports page there is no order, so this guard protects nothing. It has to be replaced before the flag goes back on — the gate being disabled in flight is a UI courtesy, not a guarantee.

The replacement: key on the resolved property identifier — the APN or SiteX location id the lookup returns, available before the spend — plus a window of minutes, not days: long enough that a double-click or refresh returns the existing profile, short enough that a genuine re-run next quarter still works, because comps move. The test that matters: two requests for the same property seconds apart spend one credit, not two.
The two environment variables
CONCIERGE_PROFILE_ENABLED = true — exact string, compared lower-cased and trimmed. Unset or malformed means OFF, deliberately, so a missing variable can never read as enabled.
SITEX_CONCIERGE_FEED_ID = 100001 — Title Profile_144. Required, with no fallback to SITEX_FEED_ID even though both are 100001 today; set in Preview and Production since 24 Aug 2026.
6 · Decisions already made
Comparables, and why the schema exists. SiteX accepts comp_* options and silently ignores them on our feed, proven with a byte-identical control — so the filtering is ours. Every candidate is stored with the first rule it failed, from a fixed list of eight, so a challenged comparable is explained from a record rather than reconstructed. maxComps is a ceiling, not a quota — seven qualifying comps means seven shown, never padded; the legacy report loosened filters until it hit a count, then printed the original criteria. Operators cannot hand-pick; they move criteria, on the issued profile, after the spend.
Spend and safety. An address resolving to anything other than exactly one property produces an error and no report, never a fallback. The presenting rep is resolved server-side, never from the browser. sitex_search_id is recorded on every call — the only handle tying a report to an invoice line.
Where it lives. A requested courtesy report, not an order document — Gerard's call, and the documents-panel.tsx note was right all along. Requiring an order would mean only a property you already hold a file on could be profiled, which is the opposite of the purpose.
Document and process. Eight pages, fixed order, letter. All data kept; visual noise removed instead, caveats as one footnote per page. No rebase of feat/concierge-operator-ui — wired fresh against main.
