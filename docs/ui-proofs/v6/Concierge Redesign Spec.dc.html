Concierge Profile redesign

This is the redesign of the eight-page document itself: what profile-document.tsx should become. The picture is Concierge Property Profile v3.dc.html, rendered from the stored 24 Aug SiteX payload for 10523 Stonybrook Ave. Concierge Profile Handover.dc.html covers wiring only, not this.

Short answer to "is it a layout job or a data job": mostly layout. Every page draws on fields you already store, or on values derived from them, with one real gap: the legal description, plus three fields to confirm are kept on transfers and owners. No time series, no photos, no neighbourhood or school data, no listing history. None of the "likely gaps" apply.

Translation rules, same as Part D of the Reports handoff

  • Tokens come from the document, not the mock. v3 uses Instrument Sans with #16324F / #C86A2A / warm greys. Keep the component's Helvetica, NAVY #1B2A4A, ORANGE #F26B2B, MUTED #526174, BORDER #D7DDE5 and TINT #F8F9FA. The redesign is about structure and hierarchy. The palette shouldn't change.
  • No flex gap. v3 relies on gap:2px tile grids throughout. Replace them with margins and the tileLast pattern.
  • Keep Shell, TEMPLATE_VERSION (bump it), the hyphenation callback, the fmt helpers, GAP/Absent and the Svg primitives.
  • Type floor rises. The current 8.5pt body and 6pt labels become 9.5pt body, 8.5pt table cells and a 7pt minimum, matching the farming family. It's the same audience across a table.

What the redesign changes, in one list

  • The value leads. Page 1 is address, then one headline value with its range, then five facts. It replaces the current three-cell metric bar.
  • Plain section names that read as sentences: The property · Owners and taxes · Ownership history · Where the comparables are · How they compare · The five sales in detail · Parcel map.
  • Each page opens with a one-line summary generated from data, e.g. "Two individuals are vested. Taxes for 2025 total $1,956 and are current."
  • One caveat per page, as a footnote line. No inline caveat tags, no category chips, no mono micro-labels.
  • Orange means one thing: foreclosure-related records and the one absence that changes the reading (no subject sale). Navy marks the current vesting deed.
  • Tax table goes from ten columns to five: installment, amount, due, delinquent after, status.
  • Comparable numbers are identical on pages 5, 6 and 7, and the page says so.

Three decisions to confirm with Gerard before building

  1. A headline value on page 1. The redesign leads with "$749,400, range $701,900 – $779,200, informational, not an appraisal." It's derived honestly, but printing a single number is a product and compliance call the current document doesn't make. If it's a no, page 1 leads with the median comparable $/sf and range instead, and the layout holds.
  2. Installments derived from the annual amount. The payload has an annual total and a status, so v3 halves it and prints California's statutory due and delinquency dates, and says so on the page. That's correct for California counties only. If coverage ever leaves California, it needs a per-state rule or the table falls back to a single annual row.
  3. Legal description: fetch or absent. Either add it to what's persisted from the payload (check the raw response first, since the v3 sample shows it was present on 24 Aug), or ship page 2 with the Absent box. Don't block the redesign on it.

Still true from earlier

  • The Concierge sample has no rep photo, so the photo gap in the farming footer doesn't apply here.
  • The comparables rules stand: stored with the first rule each failed, maxComps is a ceiling, criteria printed as applied, and no hand-picking.
  • List-page wording has been superseded since the Reports handoff. Concierge rows read Property lookup / Failed before the lookup / Failed after the lookup, with no credit language, and green means proved delivered by the event webhook, not accepted. Follow the code, not the 17 Sep handoff, on both.
